# 中期答辩问题：实验场景增强方案

## 1. 文档目的

本文档专门整理“如何把当前平台升级到更接近顶会实验设计”的场景方案，重点回答：

- 三个候选实验场景是否合理；
- 哪些场景适合作为论文主实验；
- 指标和实验组织方式还需要如何优化。

---

## 2. 建议的论文实验主线

基于老师意见与当前平台能力，建议将论文主实验收敛为以下两条主线和一条补充线：

### 主线一：轨迹驱动的边缘恢复实验

目标：

- 验证 `PMAP_ACK` 在动态边缘环境下比 `PMAP` 更能避免状态错位并完成恢复。

重点指标：

- 成功率
- 状态错位率
- 恢复成功率
- 认证时延

### 主线二：大规模并发蜂群认证实验

目标：

- 验证 `PMAP` / `PMAP_ACK` 在高并发条件下的认证效率与扩展性。

重点指标：

- 时延 CDF
- 超时率
- 每成功认证的消息数和字节数
- 成功吞吐

### 补充线：高速场景下的突发失联恢复实验

目标：

- 验证高动态链路下恢复机制是否仍有效。

当前建议：

- 先作为补充实验；
- 若物理层保真度提升后，再升为主实验。

---

## 3. 结合实验场景讨论后的进一步补充方案

核心原则：

- 不能只做“随机运动 + 平均成功率”；
- 必须把 **协议设计初衷** 与 **真实任务/物理约束** 绑定；
- 不能让实验显得“概念很强，但平台保真度不足”；
- 每个场景都要服务于一个明确的机制结论。

## 3.1 对三个候选场景的合理性判断

### 场景一：基于真实巡检轨迹的边缘去同步修复

这是目前 **最合理、最值得优先推进** 的主场景。

原因：

- 它直接命中 `PMAP_ACK` 的设计价值：避免 ACK 丢失时错误提交 `PID/CRP`；
- 与无人机移动、覆盖边缘、切换窗口高度相关；
- 真实轨迹驱动比简单随机运动更有说服力；
- 适合形成“失败 -> 恢复”的完整故事线。

需要进一步优化的点：

- 不应只用单一 `RSSI=-85dBm` 作为边缘判据，而应结合：
  - 距离 / 路径损耗
  - RSSI / SINR
  - 切换前窗口时间
  - 实际丢包概率
- 在表述上，建议区分：
  - **恶意去同步攻击**
  - **移动诱发的自然去同步（mobility-induced desynchronization）**

推荐扩展指标：

- `Success Rate vs Distance from ZSP`
- `State Mismatch Rate`
- `Recovery Completion Ratio`
- `Re-authentication Overhead`

结论：  
这个场景应当作为论文的 **主实验 A**。

### 场景二：高密度编队起飞的信令风暴压力

这是一个 **合理且必要** 的可扩展性场景，但需要避免把“链路拥塞”和“协议计算开销”混在一起。

当前构想的优点：

- 能体现无人机蜂群并发认证的网络特性；
- 能比较轻量协议和高开销协议在群体场景中的性能差异；
- 适合回答“协议是否能支撑大规模 UAV 网络”。

主要风险：

- 如果直接把 `ECC-based AKA` 作为对照，但没有足够清晰的实现依据，容易被质疑；
- 如果同时引入碰撞、排队、处理时延、超时等多种因素，最后很难定位真实性能瓶颈。

优化建议：

- 将该场景拆成两个子实验：
  - **子实验 A：纯网络拥塞可扩展性**
    - 固定协议处理代价
    - 重点观察并发数增长带来的冲突、超时和完成率变化
  - **子实验 B：计算开销敏感性**
    - 保持相同网络条件
    - 分别注入 Hash-like / ECC-like / 更重型开销
    - 观察计算时延对认证队列和超时率的影响

推荐指标：

- `CDF of Authentication Delay`
- `Timeout Probability vs Swarm Size`
- `Successful Authentication Throughput`
- `Average Queueing Delay`
- `Retransmission Count`

结论：  
这个场景适合作为论文的 **主实验 B**。

### 场景三：高速拦截下的多普勒鲁棒性测试

这个场景 **研究意义很强，但对当前平台来说实施门槛最高**。

优点：

- 它可以进一步证明协议在高动态条件下的鲁棒性；
- 能从物理层角度增强论文“不是简单逻辑仿真”的可信度。

问题：

- 需要更高保真的信道与速度建模；
- 若当前平台还不能严格体现多普勒、相干时间、天线增益变化等因素，直接宣称“多普勒鲁棒性”会显得证据不足；
- 这类实验更容易被审稿人追问仿真 fidelity。

优化建议：

- 当前阶段先把它降级表述为：
  - **高速移动下的突发失联恢复实验**
  - 或 **high-mobility burst-loss scenario**
- 重点不放在“已经做到了精确多普勒仿真”，而放在：
  - 高速移动导致链路快速波动
  - ACK / 回复更容易丢失
  - `PMAP_ACK` 的恢复机制是否仍有效

推荐指标：

- `Authentication Failure Rate vs UAV Velocity`
- `Recovery Success Ratio vs Velocity`
- `Average Re-authentication Delay vs Velocity`

结论：  
这个场景当前更适合作为 **补充实验 / 附录实验 / 后续扩展实验**，不建议现阶段作为论文主卖点。

## 3.2 更优的实验组织方式

为了避免实验线索过多、平台保真度不足的问题，建议把整体实验体系收敛成：

### 主实验 A：轨迹驱动的边缘恢复实验

目标：

- 验证 `PMAP_ACK` 在动态覆盖边缘条件下比 `PMAP` 更能避免状态错位并完成恢复。

对照协议：

- `PMAP_ACK`
- `PMAP`

实验重点：

- 真实轨迹 / 任务轨迹
- 覆盖边缘触发认证
- ACK 丢失与恢复

### 主实验 B：大规模并发蜂群认证实验

目标：

- 验证协议在高密度并发接入下的扩展性与效率。

对照协议：

- `PMAP`
- `PMAP_ACK`
- 1 个静态或预共享密钥基线
- 1 个高开销公开密钥协议（代表性实现）

实验重点：

- 10/30/50/100 UAV
- 起飞窗口集中触发认证
- 网络拥塞与计算开销分离分析

### 补充实验 C：高速移动下的突发失联恢复

目标：

- 验证在极端动态条件下，恢复机制是否仍然有效。

当前定位：

- 先做补充实验
- 平台信道建模足够完善后再升级为主实验

## 3.3 需要补充的机制级指标

建议在现有成功率、时延、消息数之外，再显式加入以下机制指标：

- **State Mismatch Rate**
  - ZSP 已更新状态而 UAV 未更新的比例
- **Recovery Completion Ratio**
  - 首次失败后能在后续窗口中恢复成功的比例
- **Protocol-Step Failure Breakdown**
  - 按 `M1 / M2 / M3_M4 / ACK / retry` 细分失败原因
- **Re-authentication Cost**
  - 最终成功前的额外消息数、额外字节数、额外时延
- **Tail Latency**
  - 95th / 99th 百分位认证时延

这些指标能更直接支撑“协议为什么更好”，而不是只给平均值。

## 3.4 当前平台为支撑这些场景还需补足的能力

### 动态任务驱动触发

- 在切换边缘、任务起飞、编队变换等时刻自动触发认证；
- 不再只依赖固定时刻触发。

### 位置相关链路状态

- 认证失败概率与位置、距离、覆盖边缘状态绑定；
- 而不是简单固定丢包。

### 多协议统一接口

- 协议实体需统一记录相同字段和指标；
- 保证对比实验可公平统计。

### 结果导出与批量实验脚本

- 自动跑不同参数组合；
- 自动导出每组结果；
- 自动绘制论文图表。

---

## 4. 结论

结合讨论后的判断是：

- 三个场景整体方向 **是合理的**；
- 其中最值得作为当前阶段主实验的是：
  - **边缘去同步恢复**
  - **高并发蜂群认证**
- 高速多普勒/极端物理层场景 **应保留，但暂不宜作为主卖点**；
- 当前平台后续工作的重点，不是再增加很多零散功能，而是：
  - 用更真实的动态任务和链路约束，
  - 把协议设计初衷映射为可测的实验现象，
  - 并通过图表和对照协议形成有说服力的论文结论。
