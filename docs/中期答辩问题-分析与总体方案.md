# 中期答辩问题：分析与总体方案

## 1. 文档目的

本文档聚焦中期答辩老师提出的问题本身，回答三个问题：

1. 老师具体质疑了什么；
2. 当前项目已经做到哪一步；
3. 后续总体应该如何改，而不是推翻重做。

---

## 2. 中期答辩问题总结

根据 `中期问题.pdf`，老师的核心意见可以归纳为以下四类：

### 2.1 当前平台没有体现“无人机网络”的动态性

老师指出，目前设计更像一个通用认证协议仿真器，没有真正体现无人机网络的特点，尤其是：

- 没有足够规模的无人机节点组成蜂群；
- 无人机运动过于简单，不能只依赖 ns-3 内置移动模块；
- 缺乏与移动、覆盖、切换、边缘失联等 UAV 网络特性相关的机制。

### 2.2 缺少量化数据与可视化结果

老师指出，当前不能只停留在命令行输出或单条日志，需要形成可量化指标并绘图，例如：

- 认证成功率
- 数据包大小 / 通信开销
- 认证平均时长

### 2.3 协议数量太少，缺少横向对比

老师指出，目前只能仿真一个协议，缺乏比较对象，因此论文结论说服力不足。需要：

- 实现多个有代表性的对比协议；
- 在尽可能大的无人机网络中做统一条件下的认证实验；
- 输出可对比的数据结果。

### 2.4 去同步机制是否还应继续推进

老师提出了一个方向性问题：去同步机制是否值得继续做。  
这本质上是在问：

- 这个问题是否足够重要；
- 是否真正体现无人机网络场景中的独特价值；
- 是否能成为论文主线，而不是一个孤立的小技巧。

---

## 3. 当前项目现状：已经完成了什么

### 3.1 已完成的平台能力

当前项目已经具备：

- **协议仿真平台基础闭环**  
  前端创建任务 -> 后端生成任务配置 -> NS-3 调起仿真 -> 实体输出 JSONL 日志 -> 后端分析 -> 前端展示指标与时间线。

- **两种 D2Z 协议模式**
  - `PMAP`
  - `PMAP_ACK`

- **去同步与恢复机制**
  - ACK 丢失场景下，`PMAP_ACK` 可以保持旧 `PID/CRP` 并重试；
  - 支持首次触发的去同步模板，便于观察恢复路径。

- **统一日志与分析能力**
  - 事件、会话、时间线、性能指标；
  - 已可统计成功率、消息数、通信开销、耗时、错误分布。

- **前端实验入口**
  - 已有多种场景预设；
  - 已支持按任务 ID 分析结果；
  - 已支持复制任务 ID，提高实验复现效率。

### 3.2 当前最主要的短板

虽然平台闭环已经打通，但老师指出的问题依然成立，主要短板是：

- **动态性不足**：运动模型还比较简单；
- **任务语义不足**：认证触发与 UAV 任务行为、覆盖边缘、群体调度没有强绑定；
- **协议对照不足**：目前协议数量仍不够支撑论文对比；
- **图表不足**：虽然已有分析指标，但尚未形成论文级图表体系。

因此，接下来的重点不是“重写平台”，而是：  
**在现有底座上，把动态场景、协议对照、图表输出做深做强。**

---

## 4. 总体改进思路

针对老师的问题，本项目后续改进采用以下总体路线：

### 路线一：从“单次认证仿真”升级为“动态无人机网络实验平台”

重点解决：

- 蜂群规模
- 任务驱动运动
- 覆盖切换
- 边缘认证
- 群体并发

### 路线二：从“单协议演示”升级为“多协议统一对比实验框架”

重点解决：

- 统一协议接口
- 多协议任务配置
- 同场景下统一评测
- 输出横向可比指标

### 路线三：从“日志可读”升级为“论文图表可用”

重点解决：

- 自动计算指标
- 自动生成实验数据文件
- 自动绘制图表
- 形成论文可直接引用的实验结果

## 5. 针对每个答辩问题的改进方案

## 5.1 问题一：未体现无人机移动的动态性

### 问题本质

当前平台虽然使用了 ns-3 的移动组件，但无人机运动仍偏“静态配置 + 简单轨迹播放”，没有真正体现 UAV 网络区别于普通 IoT 网络的特点，例如：

- 高动态拓扑
- 覆盖切换
- 群体协同运动
- 边缘触发认证
- 高速移动下链路质量波动

### 改进目标

建立一个能够体现 UAV 网络特性的动态仿真层，至少支持：

1. 基于真实轨迹或任务轨迹的巡检移动
2. 多无人机编队/群飞运动
3. 高速拦截或快速转场移动

### 具体方案

- 构建任务驱动的运动调度机制，而不是只依赖 ns-3 内置 Waypoint
- 引入蜂群规模场景：10 / 30 / 50 / 100 UAV
- 把认证触发条件与物理位置绑定，而不是固定时刻触发

### 预期结果

平台将从“协议功能仿真”升级为“面向动态 UAV 网络的协议实验平台”。

---

## 5.2 问题二：缺少可量化结果和图像

### 问题本质

老师关心的不是有没有日志，而是：

- 能不能形成统计结果
- 能不能画出图
- 能不能支撑论文结论

### 改进目标

构建“仿真 -> 指标 -> 数据文件 -> 图表”的自动化输出链路。

### 具体方案

- 扩展指标体系：
  - 认证成功率 / 失败率
  - 平均认证时延
  - 认证时延 CDF
  - 总消息数 / 总字节数
  - 每成功会话开销
  - 状态错位率
  - 恢复成功率
- 增加结果导出：
  - CSV
  - JSON
  - Matplotlib / Plotly 图像
- 在前端逐步增加结果图表页

### 预期结果

项目将具备自动出指标、自动出图、自动协议对比的能力。

---

## 5.3 问题三：当前只能仿真一个协议

### 问题本质

没有对比协议，就很难说明当前协议设计更优。

### 当前基础

项目已不是严格意义上的“只有一个协议”，而是已经有：

- `PMAP`
- `PMAP_ACK`

但仍缺少经典基线协议与高开销对照协议。

### 改进目标

形成“目标协议 + 基线协议 + 高开销对照协议”的多协议实验框架。

### 具体方案

- 第一阶段：完善 `PMAP` / `PMAP_ACK` 内部对比
- 第二阶段：加入静态/预共享身份基线协议
- 第三阶段：加入高开销公开密钥协议（代表性实现）

### 对“无源码协议说服力存疑”的应对

- 优先选文献中流程清晰的协议
- 明确写出实现假设
- 结论聚焦机制层面对比，不夸大为“完全复现”

---

## 5.4 问题四：去同步机制是否需要继续做

### 结论

**需要继续做，而且应当保留为项目主线之一。**

### 原因

去同步问题不是一个孤立漏洞，而是 UAV 动态网络中非常自然的状态不一致现象，尤其在：

- 覆盖边缘
- ACK 丢失
- 切换前窗口
- 高动态链路

这些条件下，ZSP 与 UAV 对认证是否完成的认知不同步，是合理且高价值的问题。

### 后续定位建议

建议把去同步机制放在如下叙事中：

- 问题：动态 UAV 网络中，确认消息易丢失，导致认证状态不一致
- 风险：设备掉线、重复认证、状态失配、服务中断
- 方案：`PMAP_ACK` 通过 ACK 驱动提交，避免错误轮换
- 价值：提高恢复成功率，降低状态错位率

也建议区分：

- **恶意去同步攻击**
- **移动诱发的自然去同步（mobility-induced desynchronization）**

这样更容易获得老师和评审认可。

---

## 6. 总结

这部分结论可以概括为：

- 当前平台不是从零开始，而是已经有较完整底座；
- 后续重点不是重做，而是在现有基础上增强：
  - 动态性
  - 对比性
  - 图表化
- 去同步机制应该继续做，但要提升为“动态网络中的认证状态恢复问题”。
